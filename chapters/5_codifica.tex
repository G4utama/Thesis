\section{Tecnologie e strumenti}
\label{Tecnologie e strumenti}

\subsection{Linguaggio e piattaforma}
Il \textit{middleware} è stato sviluppato in \nameref{Java} e gestito tramite \nameref{Apache Maven} come \textit{build tool}, che si occupa della risoluzione delle dipendenze, della compilazione e del \textit{packaging} dell'applicazione in un \textcolor{purple}{jar} eseguibile.

\subsubsection{Java}
\label{Java}
Java è un linguaggio di programmazione ad alto livello, orientato agli oggetti e a tipizzazione statica, che si appoggia sull'omonima piattaforma \textit{software} di esecuzione, specificamente progettato per essere il più possibile indipendente dalla piattaforma \textit{hardware} di esecuzione (tramite compilazione in \textit{bytecode} prima e interpretazione poi da parte di una \acrshort{JVM}).
\begin{figure}[H]
    \centering
    \includegraphics[width=0.2\textwidth]{assets/java.png}
    \caption{Java}
\end{figure}

\paragraph{Valore aggiunto al progetto}
La tipizzazione statica di Java consente di individuare in fase di compilazione gran parte degli errori legati a un utilizzo scorretto dei contratti dei messaggi (\textcolor{purple}{OrderEvent}, \textcolor{purple}{EnrichedOrder}), un aspetto rilevante in un \textit{middleware} in cui la correttezza del formato dei dati scambiati è centrale. Inoltre, l'ecosistema Java è quello su cui si basa nativamente l'intero \textit{stack} tecnologico impiegato (\nameref{Spring}, i \textit{client} ufficiali di \nameref{Apache Kafka} e i \textit{driver} \acrshort{JDBC} per \nameref{PostgreSQL}), garantendo la massima compatibilità e il supporto per ciascuna di queste componenti.

\paragraph{Punti deboli}
Rispetto a linguaggi più recenti pensati specificamente per microservizi \textit{cloud-native}, Java presenta un tempo di avvio della \acrshort{JVM} e un consumo di memoria a \textit{runtime} superiori.

\paragraph{Competitor principali}
\begin{itemize}
    \item \textbf{C\#:} principale linguaggo concorrente per lo sviluppo di applicazioni enterprise di questo tipo;
    \item \textbf{Kotlin:} in ambito \acrshort{JVM}, quindi più facilmente compatibile con le librerie Java impiegate nel progetto.
\end{itemize}

\paragraph{Motivazione della scelta}
La scelta di Java è coerente con l'obiettivo del tirocinio, che prevedeva esplicitamente lo studio e l'implementazione del \textit{middleware} tramite il framework \nameref{Spring}, basato su Java. Inoltre, la maggior integrazione di Java con Kafka e \acrshort{JPA} lo rende una scelta più solida, in questo contesto specifico.

\subsubsection{Apache Maven}
\label{Apache Maven}
Apache Maven è uno strumento di gestione di progetti \textit{software} basati su \nameref{Java} e \textit{build automation}. \\
Maven usa un costrutto conosciuto come \acrshort{POM}; un file \acrshort{XML} che descrive le dipendenze fra il progetto, le varie versioni di librerie necessarie e le dipendenze fra di esse. In questo modo si separano le librerie dalla \textit{directory} di progetto utilizzando questo file descrittivo per definirne le relazioni. \\
Maven effettua automaticamente il \textit{download} di librerie \nameref{Java} e \textit{plug-in} Maven dai vari \textit{repository} definiti scaricandoli in locale o in un \textit{repository} centralizzato lato sviluppo. Questo permette di recuperare in modo uniforme i vari file \acrshort{JAR} e di poter spostare il progetto indipendentemente da un ambiente all'altro avendo la sicurezza di utilizzare sempre le stesse versioni delle librerie.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\textwidth]{assets/apacheMaven.png}
    \caption{Apache Maven}
\end{figure}

\paragraph{Valore aggiunto al progetto}
Maven ha permesso di dichiarare in modo esplicito e riproducibile l'intero insieme di dipendenze del progetto (\textcolor{purple}{spring-kafka}, \textcolor{purple}{spring-boot-starter-data-jpa}, driver \textcolor{purple}{postgresql}, \gls{Lombok}, ...), requisito importante per la riproducibilità dell'ambiente descritta anche a proposito di \nameref{Docker}.

\paragraph{Punti deboli}
Maven non dispone nativamente di un sistema di \textit{caching} incrementale delle build avanzato quanto quello di alcuni concorrenti, aspetto che può diventare un limite in progetti di dimensioni maggiori con tempi di \textit{build} più lunghi.

\paragraph{Competitor principali}
\begin{itemize}
    \item \textbf{Gradle:} utilizza uno \textit{script} basato su Groovy o Kotlin al posto dell'\acrshort{XML} e offre un sistema di \textit{build} incrementale generalmente più \textit{performante}.
\end{itemize}

\paragraph{Motivazione della scelta}
Maven è stato preferito a Gradle principalmente per la sua maggiore diffusione e documentazione nell'ambito specifico dei progetti \nameref{Spring Boot}, nonché per la maggiore semplicità del formato dichiarativo \acrshort{XML} rispetto a uno \textit{script} Groovy/Kotlin.

\subsection{Framework applicativo}
Il progetto si basa principalmente sul framework Spring, in particolare i seguenti moduli:
\begin{itemize}
    \item \textbf{Spring Boot:} per semplificare la configurazione e l'avvio di applicazioni Java
    \item \textbf{Spring Data JPA:} per la persistenza dei dati
    \item \textbf{Spring Kafka:} per l'integrazione dichiarativa con \nameref{Apache Kafka} (consumer, producer, listener)
\end{itemize}

\subsubsection{Spring}
\label{Spring}
Spring è un framework \gls{Open Source} per lo sviluppo di applicazioni su piattaforma Java.
A questo framework sono associati tanti altri progetti, che hanno nomi composti come Spring Boot, Spring Data JPA e Spring Kafka.
Questi progetti sono stati ideati per fornire funzionalità aggiuntive al framework.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\textwidth]{assets/spring.png}
    \caption{Spring}
\end{figure}

\paragraph{Valore aggiunto al progetto}
Spring, tramite i suoi moduli specializzati, fornisce per ciascuna delle fasi tipiche del \textit{middleware} un'astrazione dedicata: \textbf{Spring Boot}, \textbf{Spring Data JPA} , \textbf{Spring Kafka}.

\paragraph{Punti deboli}
Spring Boot ha un \textit{footprint} di memoria e un tempo di avvio superiori rispetto a framework concorrenti pensati specificamente per ambienti \textit{cloud-native} con \textit{scaling} rapido, aspetto non critico per il \textit{middleware} sviluppato, ma potenzialmente rilevante in un contesto di produzione con requisiti di scalabilità orizzontale molto stringenti.

\paragraph{Competitor principali}
\begin{itemize}
    \item \textbf{Quarkus} e \textbf{Micronaut}: principali \textit{framework} concorrenti in ambito Java enterprise, entrambi progettati specificamente per ridurre tempo di avvio e consumo di memoria in ambienti containerizzati;
    \item \textbf{Jakarta EE:} standard enterprise su cui lo stesso Spring si è storicamente ispirato;
    \item \textbf{Apache Camel:} \textit{framework} di integrazione che implementa nativamente numerosi \textit{Enterprise Integration Patterns} (si veda \ref{Progettazione}).
\end{itemize}

\paragraph{Motivazione della scelta}
Spring è stato indicato esplicitamente come tecnologia di riferimento per l'attività di tirocinio, in coerenza con il suo ruolo di \textit{framework enterprise} \nameref{Java} più diffuso e documentato.

\subsection{Infrastruttura di supporto}
L'ambiente di sviluppo è orchestrato tramite Docker e Docker Compose, secondo la definizione riportata nel \textit{file} \textcolor{purple}{docker-compose.yml}, che avvia tre servizi containerizzati:
\begin{itemize}
    \item \textbf{PostgreSQL:} il \textit{database} relazionale che ospita i dati di arricchimento;
    \item \textbf{Apache Kafka:} configurato in modalità KRaft (Kafka Raft), l'architettura più recente che elimina la dipendenza da Apache ZooKeeper per il coordinamento del \textit{cluster}, unificando i ruoli di \textit{broker} e \textit{controller} in un singolo nodo (scelta adeguata a un ambiente di sviluppo locale a singolo nodo);
    \item \textbf{Kafka UI:} un'interfaccia web (esposta sulla porta \textcolor{purple}{8081}) che consente di ispezionare topic, partizioni, messaggi e \textit{consumer group} senza dover ricorrere alla sola riga di comando.
\end{itemize}
Questa infrastruttura consente di riprodurre in locale, in modo rapido e ripetibile, un ambiente rappresentativo di un \textit{deployment} di produzione, mantenendo però la semplicità necessaria in fase di sviluppo e test.

\subsubsection{Docker}
\label{Docker}
Docker è un popolare \textit{software} libero che utilizza la virtualizzazione a livello di sistema operativo per eseguire applicazioni in ambienti isolati chiamati \textit{container}. \\
I container Docker sono un'estensione dei \textit{container} del sistema operativo. Docker supporta sia i container Linux che quelli Windows. È possibile utilizzare Docker con container Linux anche nei sistemi Windows e MacOS grazie a tecniche di virtualizzazione.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\textwidth]{assets/docker.png}
    \caption{Docker}
\end{figure}

\paragraph{Valore aggiunto al progetto}
Docker Compose ha permesso di definire, in un unico \textit{file} dichiarativo, l'intero ambiente necessario al funzionamento del \textit{middleware} (\nameref{PostgreSQL}, \nameref{Apache Kafka} e Kafka UI), rendendolo riproducibile con un singolo comando su qualsiasi macchina di sviluppo, senza necessità di installare manualmente ciascun componente. Questo ha semplificato notevolmente sia lo sviluppo sia l'eventuale verifica del funzionamento del sistema, descritta in \ref{Implementazione}.

\paragraph{Punti deboli}
La virtualizzazione a livello di sistema operativo, per quanto più leggera rispetto a una macchina virtuale tradizionale, introduce comunque un certo \textit{overhead} prestazionale rispetto all'esecuzione nativa. Inoltre, Docker richiede l'esecuzione di un \textit{daemon} centrale, tipicamente con privilegi elevati, aspetto che pone alcune criticità di sicurezza note e mitigate solo parzialmente rispetto ad alternative più recenti.

\paragraph{Competitor principali}
\begin{itemize}
    \item \textbf{Podman:} compatibile con le stesse immagini e con gli stessi file \textit{compose} di Docker, ma con un'architettura \textit{daemonless} e supporto nativo per l'esecuzione senza privilegi di amministratore (\textit{rootless}).
\end{itemize}

\paragraph{Motivazione della scelta}
Docker è stato scelto per la sua diffusione, garantendo la disponibilità di immagini ufficiali già pronte per tutti i componenti necessari (\textcolor{purple}{postgres}, \textcolor{purple}{confluentinc/cp-kafka}, \textcolor{purple}{provectuslabs/kafka-ui}) e un'ampia documentazione. Rispetto a Podman, che pure avrebbe garantito funzionalità equivalenti con un modello di sicurezza migliore, Docker è stato preferito per la maggiore familiarità con lo strumento al momento dell'inizio del tirocinio.

\subsubsection{PostgreSQL}
\label{PostgreSQL}
PostgreSQL è un completo \acrshort{DBMS} ad oggetti pubblicato con licenza libera (stile Licenza BSD). Spesso abbreviato come "Postgres", sebbene questo sia un nome vecchio dello stesso progetto, è una reale alternativa sia rispetto ad altri prodotti liberi come MySQL, Firebird SQL e MaxDB che a quelli a codice chiuso come Oracle, IBM Informix o DB2 ed offre caratteristiche uniche nel suo genere che lo pongono per alcuni aspetti all'avanguardia nel settore delle basi di dati.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.3\textwidth]{assets/postgresql.png}
    \caption{PostgreSQL}
\end{figure}

\paragraph{Valore aggiunto al progetto}
La piena conformità \acrshort{ACID} di PostgreSQL e la sua integrazione con \nameref{Spring} tramite \textit{Spring Data JPA}/\gls{Hibernate} hanno permesso di realizzare l'accesso ai dati senza scrivere \textit{query} \acrshort{SQL} esplicite (descritto in \ref{Implementazione}).

\paragraph{Punti deboli}
Per il caso d'uso specifico del progetto, la piena potenza relazionale di PostgreSQL risulta in parte sovradimensionata. Un \textit{database} più leggero sarebbe stato sufficiente in un contesto di solo sviluppo o test.

\paragraph{Competitor principali}
\begin{itemize}
    \item \textbf{MySQL} e \textbf{MariaDB:} tra i \acrshort{DBMS} \textit{open source} relazionali più diffusi;
    \item \textbf{MongoDB:} \textit{database} \acrshort{NoSQL} documentale, per scenari in cui il modello dei dati fosse meno strutturato.
\end{itemize}

\paragraph{Motivazione della scelta}
PostgreSQL è stato scelto per la sua licenza libera, per la piena conformità agli standard \acrshort{SQL} e \acrshort{ACID} e per il supporto nativo offerto da Spring Data JPA/Hibernate. A differenza di un \textit{database} \acrshort{NoSQL}, la natura intrinsecamente strutturata e a schema fisso dei dati cliente (nome, email, città) rende inoltre un modello relazionale la scelta più naturale.

\subsubsection{Apache Kafka}
\label{Apache Kafka}
Apache Kafka è una piattaforma \gls{Open Source} di \textit{stream processing} scritta in Java e Scala e sviluppata dall'Apache Software Foundation. Il progetto mira a creare una piattaforma a bassa latenza ed alta velocità per la gestione di \textit{feed} dati in tempo reale. \\
Questo progetto viene usato principalmente per tutte le applicazioni di elaborazioni di \textit{stream} di dati in tempo reale.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\textwidth]{assets/apacheKafka.png}
    \caption{Apache Kafka}
\end{figure}

\paragraph{Valore aggiunto al progetto}
Kafka costituisce l'infrastruttura di messaggistica su cui si fonda l'intero \textit{middleware}, fungendo sia da sorgente (\textcolor{purple}{orders-input}) sia da destinazione (\textcolor{purple}{orders-output}, \textcolor{purple}{orders-input-dlq}) del flusso di dati (descritto in \ref{Progettazione}). La sua caratteristica di persistenza dei messaggi su disco, unita al disaccoppiamento temporale tra produttori e consumatori, ha permesso di realizzare un sistema resiliente. Un'eventuale indisponibilità temporanea di \nameref{PostgreSQL} non comporta la perdita di alcun evento, poiché i messaggi restano disponibili sul \textit{topic} finché non vengono correttamente elaborati.

\paragraph{Punti deboli}
Kafka introduce una complessità di configurazione e gestione superiore rispetto a un semplice \textit{message broker}, complessità che, per un volume di messaggi contenuto come quello gestito nell'ambito del progetto, non viene pienamente ripagata dai suoi vantaggi distintivi (\textit{\gls{Throughput}} elevato, scalabilità orizzontale su più nodi).

\paragraph{Competitor principali}
\begin{itemize}
    \item \textbf{RabbitMQ} e \textbf{ActiveMQ:} \textit{message broker} tradizionali orientati alle code piuttosto che allo \textit{streaming} persistente di eventi;
    \item \textbf{Apache Pulsar:} piattaforma di \textit{event streaming} più recente con un'architettura che separa \textit{storage} e \textit{serving}.
\end{itemize}

\paragraph{Motivazione della scelta}
La scelta di Apache Kafka è stata indicata esplicitamente come requisito del progetto di tirocinio. Rispetto ad alternative come RabbitMQ, Kafka offre nativamente la possibilità di rileggere lo storico dei messaggi (\textit{replay}) grazie alla persistenza configurabile, caratteristica non scontata nei tradizionali \textit{message broker} orientati alle code, dove un messaggio consumato viene tipicamente rimosso dalla coda.

\section{Progettazione}
\label{Progettazione}
Prima di procedere all'implementazione, sono state definite alcune scelte progettuali riguardanti il modello dei dati, la struttura dei \gls{Topic Kafka} e la gestione degli errori.

\subsection{Modello dei dati}
Sono stati definiti tre tipi di oggetti, ciascuno con una responsabilità precisa:
\begin{itemize}
    \item \textcolor{purple}{OrderEvent}: rappresenta il messaggio grezzo in ingresso, contenente un identificativo dell'ordine (\textcolor{purple}{orderId}), un riferimento al cliente (\textcolor{purple}{customerId}) e i dati dell'ordine stesso (\textcolor{purple}{product}, \textcolor{purple}{amount});
    \item \textcolor{purple}{Customer}: entità contenente i dati del cliente (\textcolor{purple}{fullName}, \textcolor{purple}{email}, \textcolor{purple}{city}) necessari all'arricchimento;
    \item \textcolor{purple}{EnrichedOrder}: rappresenta il messaggio finale pubblicato in uscita, che unisce i dati dell'ordine originario con i dati del cliente recuperati da \nameref{PostgreSQL}, più un \textit{timestamp} (\textcolor{purple}{enrichedAt}) che documenta il momento dell'arricchimento.
\end{itemize}
Questa separazione segue il pattern \nameref{Content Enricher}: il messaggio in ingresso è  "povero", mentre il contratto in uscita è "arricchito" con informazioni che il produttore originario dell'evento non possiede.

\label{Progettazione dei topic Kafka}

Il numero di partizioni maggiore per i topic di flusso principale (\textcolor{purple}{orders-input}, \textcolor{purple}{orders-output}) consente il parallelismo in lettura/scrittura descritto in \ref{Event Streaming}.
La singola partizione per la \acrshort{DLQ} riflette invece un volume atteso più basso e la priorità data alla semplicità di ispezione rispetto al parallelismo.

\subsection{Progettazione del flusso di elaborazione}
Il flusso di elaborazione è stato progettato secondo la seguente sequenza logica:
\begin{enumerate}
    \item un evento ordine viene pubblicato su \textcolor{purple}{orders-input};
    \item il middleware consuma il messaggio;
    \item il middleware tenta di recuperare i dati del cliente corrispondente su \nameref{PostgreSQL};
    \begin{enumerate}
        \item se il cliente viene trovato, viene composto il messaggio arricchito e pubblicato su \textcolor{purple}{orders-output};
        \item se il cliente non viene trovato, l'evento originario viene instradato su \textcolor{purple}{orders-input-dlq}, secondo il pattern \nameref{Dead Letter Channel} descritto in \ref{Dead Letter Channel};
    \end{enumerate}
\end{enumerate}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\textwidth]{assets/flusso.drawio.png}
    \caption{Flusso di elaborazione}
\end{figure}
Questa progettazione garantisce che, in caso di arresto anomalo dell'applicazione tra la lettura del messaggio e la sua elaborazione completa, il messaggio venga riletto al riavvio (semantica at-least-once, discussa in \ref{Semantica di consegna}), evitando così perdite di dati a scapito di un'eventuale elaborazione duplicata.

\section{Implementazione}
\label{Implementazione}
L'implementazione riprende le scelte progettuali descritte in \ref{Progettazione}, organizzandole in \textit{package} distinti secondo una logica di separazione delle responsabilità.
In questa sezione, oltre a presentare il codice, viene data particolare attenzione al significato e alla funzione delle \gls{Annotazioni} impiegate, elemento caratterizzante dello stile dichiarativo tipico di \nameref{Spring Boot}.

\subsection{Main}
\begin{codelisting}[H]
\begin{minted}[fontsize=\small,frame=single,framesep=10pt]{java}
@SpringBootApplication
public class EnrichmentMiddlewareApplication {
    public static void main(String[] args) {
        SpringApplication
            .run(EnrichmentMiddlewareApplication.class, args);
    }
}
\end{minted}
\caption{EnrichmentMiddlewareApplication}
\end{codelisting}
\noindent
\textcolor{purple}{@SpringBootApplication} è un'annotazione che ne racchiude tre:
\begin{itemize}
    \item \textcolor{purple}{@SpringBootConfiguration} (specializzazione di \textcolor{purple}{@Configuration}): indica che la classe può definire \gls{Bean} gestiti dal container \nameref{Spring};
    \item \textcolor{purple}{@EnableAutoConfiguration}: attiva il meccanismo di \textit{auto-configuration} di \nameref{Spring Boot}, che analizza le dipendenze presenti nel classpath e configura automaticamente i \gls{Bean} necessari;
    \item \textcolor{purple}{@ComponentScan}: scansiona il \textit{package} corrente alla ricerca di classi annotate con gli stereotipi (\textcolor{purple}{@Component}, \textcolor{purple}{@Service}, ...), registrandole automaticamente come \gls{Bean}.
\end{itemize}
Grazie a questa singola annotazione, l'intera applicazione viene rilevata e collegata automaticamente all'avvio, senza configurazione esplicita.

\subsection{Modello dei dati}
L'entità \textcolor{purple}{Customer}, mappata sulla tabella \textcolor{purple}{customers} di \nameref{PostgreSQL}:
\begin{codelisting}[H]
\begin{minted}[fontsize=\small,frame=single,framesep=10pt]{java}
@Entity
@Table(name = "customers")
@Getter 
@Setter 
@NoArgsConstructor 
@AllArgsConstructor
public class Customer {
    @Id
    private Long id;
    @Column(name = "full_name", nullable = false)
    private String fullName;
    @Column(name = "email")
    private String email;
    @Column(name = "city")
    private String city;
}
\end{minted}
\caption{Customer}
\end{codelisting}
\noindent
Le annotazioni Jakarta Persistence (\acrshort{JPA}), elaborate da \gls{Hibernate} a \textit{runtime}, definiscono il \textit{mapping} tra la classe \nameref{Java} e la tabella del \textit{database}:
\begin{itemize}
    \item \textcolor{purple}{@Entity}: dichiara che la classe è un'entità persistente, cioè un oggetto il cui stato può essere salvato e recuperato dal database tramite \acrshort{JPA};
    \item \textcolor{purple}{@Table(name = "customers")}: specifica esplicitamente il nome della tabella a cui l'entità è mappata (in assenza di questa annotazione, \acrshort{JPA} userebbe per convenzione il nome della classe);
    \item \textcolor{purple}{@Id}: indica il campo che costituisce la chiave primaria della tabella;
    \item \textcolor{purple}{@Column(...)}: mappa un campo della classe su una colonna specifica, permettendo di personalizzarne il nome e i vincoli (ad esempio \textcolor{purple}{nullable = false}, che impone che il campo non possa essere nullo).
\end{itemize}
Le annotazioni \gls{Lombok}, agiscono in fase di compilazione: il compilatore, tramite un \textit{annotation processor}, genera automaticamente il codice sorgente corrispondente, che viene poi incluso nel \textit{bytecode} risultante, senza che sia visibile nel file:
\begin{itemize}
    \item \textcolor{purple}{@Getter} / \textcolor{purple}{@Setter}: generano rispettivamente i metodi \textit{getter} (\textcolor{purple}{getFullName()}, \textcolor{purple}{getEmail()}, ...) e i metodi \textit{setter} (\textcolor{purple}{setFullName(...)}, ...) per tutti i campi della classe;
    \item \textcolor{purple}{@NoArgsConstructor}: genera un costruttore vuoto (senza argomenti), richiesto obbligatoriamente dalla specifica \acrshort{JPA}, poiché \gls{Hibernate} deve poter istanziare l'entità tramite \textit{reflection} prima di popolarne i campi;
    \item \textcolor{purple}{@AllArgsConstructor}: genera un costruttore che accetta un parametro per ciascun campo della classe, utile per la creazione di istanze (ad esempio nei test).
\end{itemize}
I \acrshort{DTO} che rappresentano i contratti dei messaggi Kafka seguono un'impostazione analoga, con l'aggiunta di un'ulteriore annotazione \gls{Lombok}:

\end{codelisting}
\begin{itemize}
    \item \textcolor{purple}{@ToString}: genera un'implementazione del metodo \textcolor{purple}{toString()} che elenca automaticamente il nome e il valore di ciascun campo, particolarmente utile in fase di \textit{logging} (come si vedrà in \textcolor{purple}{OrderConsumer}, dove l'oggetto \textcolor{purple}{OrderEvent} viene loggato direttamente).
\end{itemize}
\subsection{Accesso ai dati}
L'accesso a \nameref{PostgreSQL} è realizzato tramite un \textit{repository} \nameref{Spring Data JPA}, che estende \textcolor{purple}{JpaRepository} senza necessità di implementazioni aggiuntive:
\begin{codelisting}[H]
\begin{minted}[fontsize=\small,frame=single,framesep=10pt]{java}
public interface CustomerRepository 
    extends JpaRepository<Customer, Long> {
    
}
\end{minted}
\caption{CustomerRepository}
\end{codelisting}
\noindent
Qui non compaiono annotazioni esplicite: è sufficiente che l'interfaccia estenda \textcolor{purple}{JpaRepository<Customer, Long>} (dove \textcolor{purple}{Customer} è il tipo dell'entità e \textcolor{purple}{Long} il tipo della sua chiave primaria) perché \nameref{Spring Data JPA} generi automaticamente, a \textit{runtime}, un'implementazione proxy dell'interfaccia, fornendo di \textit{default} i metodi \acrshort{CRUD} più comuni (\textcolor{purple}{findById}, \textcolor{purple}{save}, \textcolor{purple}{deleteById}, \textcolor{purple}{findAll}, ...). \\ \\
Questo meccanismo, che non richiede annotazioni perché il comportamento è determinato dall'interfaccia ereditata, è ciò che permette al progetto di interrogare \nameref{PostgreSQL} senza scrivere alcuna query \acrshort{SQL} esplicita.

\subsection{Logica di enrichment}
Il cuore applicativo del pattern \nameref{Content Enricher} è la classe \textcolor{purple}{EnrichmentService}:
\begin{codelisting}[H]
\begin{minted}[fontsize=\small,frame=single,framesep=10pt]{java}
@Slf4j
@Service
@RequiredArgsConstructor
public class EnrichmentService {

    private final CustomerRepository customerRepository;

    @Transactional(readOnly = true)
    public EnrichedOrder enrich(OrderEvent orderEvent) {
        Customer customer = customerRepository
            .findById(orderEvent.getCustomerId())
            .orElseThrow(() -> 
            new CustomerNotFoundException(orderEvent.getCustomerId()));

        return new EnrichedOrder(
                orderEvent.getOrderId(),
                orderEvent.getCustomerId(),
                customer.getFullName(),
                customer.getEmail(),
                customer.getCity(),
                orderEvent.getProduct(),
                orderEvent.getAmount(),
                Instant.now()
        );
    }
}
\end{minted}
\caption{EnrichmentService}
\end{codelisting}
\noindent
Questa classe è composta da quattro annotazioni:
\begin{itemize}
    \item \textcolor{purple}{@Slf4j}: inietta automaticamente un campo statico \textcolor{purple}{log} di tipo \textcolor{purple}{Logger}, consente di scrivere direttamente \textcolor{purple}{log.debug(...)}.
    \item \textcolor{purple}{@Service}: è una specializzazione di \textcolor{purple}{@Component}, che identifica la classe come componente contenente logica di business. Dal punto di vista del container \nameref{Spring} il comportamento è identico a \textcolor{purple}{@Component} (la classe viene rilevata dal \textcolor{purple}{@ComponentScan} e registrata come \gls{Bean}), ma l'uso di \textcolor{purple}{@Service} comunica esplicitamente l'intento architetturale della classe, migliorando la leggibilità del codice.
    \item \textcolor{purple}{@RequiredArgsConstructor}: genera un costruttore con un parametro per ciascun campo dichiarato \textcolor{purple}{final} (in questo caso \textcolor{purple}{customerRepository}). Combinata con l'assenza di un costruttore esplicito, questa annotazione realizza la \textit{dependency injection} tramite costruttore: \nameref{Spring}, individuando un unico costruttore, lo invoca automaticamente iniettando il \gls{Bean} \textcolor{purple}{CustomerRepository} disponibile nel \textit{container}. Questo approccio è preferibile rispetto all'iniezione tramite campo (\textcolor{purple}{@Autowired}), poiché rende le dipendenze esplicite, immutabili e facilmente testabili.
    \item \textcolor{purple}{@Transactional(readOnly = true)}: delimita una transazione database attorno all'esecuzione del metodo \textcolor{purple}{enrich}. Il parametro \textcolor{purple}{readOnly = true} segnala esplicitamente che il metodo esegue solo operazioni di lettura, permettendo a \gls{Hibernate} di applicare alcune ottimizzazioni (ad esempio disabilitando il \textit{dirty checking}, ovvero il meccanismo che traccia le modifiche alle entità per determinare se sia necessario un aggiornamento sul database). Sebbene nel caso specifico l'operazione compiuta sia una singola \textit{query}, l'uso esplicito di \textcolor{purple}{@Transactional} rende il comportamento robusto anche a future estensioni del metodo che coinvolgano più interrogazioni.
\end{itemize}

\subsection{Consumer}
Il \textit{listener} Kafka orchestra l'intero flusso:
\begin{codelisting}[H]
\begin{minted}[fontsize=\small,frame=single,framesep=10pt]{java}
@Slf4j
@Component
@RequiredArgsConstructor
public class OrderConsumer {

    private final EnrichmentService enrichmentService;
    private final EnrichedProducer producer;

    @KafkaListener(
            topics = "${app.kafka.topic.input}",
            groupId = "${spring.kafka.consumer.group-id}"
    )
    public void consume(ConsumerRecord<String, OrderEvent> record, 
        Acknowledgment ack) {
        String key = record.key();
        OrderEvent orderEvent = record.value();

        try {
            EnrichedOrder enriched = enrichmentService
                .enrich(orderEvent);
            producer.sendEnriched(key, enriched);
            ack.acknowledge();

        } catch (CustomerNotFoundException e) {
            producer.sendToDlq(key, orderEvent);
            ack.acknowledge();

        } catch (Exception e) {
            
        }
    }
}
\end{minted}
\caption{OrderConsumer}
\end{codelisting}
\begin{itemize}
    \item \textcolor{purple}{@Component}: indica che la classe deve essere gestita come \gls{Bean} dal \textit{container}. Usato, invece di \textcolor{purple}{@Service}, perché la classe non contiene logica di business.
    \item \textcolor{purple}{@KafkaListener}: è l'annotazione che realizza concretamente il modello \textit{listener} descritto in \ref{Spring Kafka}. Applicata a un metodo, ne fa un punto di ricezione automatica dei messaggi pubblicati sul topic specificato:
    \begin{itemize}
        \item \textcolor{purple}{topics = "\${app.kafka.topic.input}"}: il nome del topic da ascoltare non è scritto staticamente, ma iniettato da configurazione tramite la sintassi \textit{placeholder} \textcolor{purple}{\${...}}, che Spring risolve leggendo la proprietà corrispondente da \textcolor{purple}{application.yml} (in questo caso \textcolor{purple}{orders-input}). Questo disaccoppia il codice dal valore concreto del nome del topic, rendendolo configurabile per ambiente (sviluppo, test, produzione) senza modifiche al codice sorgente;
        \item \textcolor{purple}{groupId = "\${spring.kafka.consumer.group-id}"}: allo stesso modo, il \textit{consumer group} (introdotto in \ref{Architettura e concetti fondamentali}) è delegato in configurazione.
    \end{itemize}
    Il metodo annotato accetta come parametri un \textcolor{purple}{ConsumerRecord<String, OrderEvent>}, l'involucro nativo del \textit{client} Kafka che espone, oltre al \textit{payload} deserializzato, anche metadati quali topic, partizione e \textit{offset}, e un oggetto \textcolor{purple}{Acknowledgment}, che rappresenta il meccanismo tramite cui il metodo conferma esplicitamente l'elaborazione del messaggio (\textcolor{purple}{ack.acknowledge()}), coerentemente con la modalità \textcolor{purple}{ack-mode: manual} configurata in \textcolor{purple}{application.yml}.
\end{itemize}
La \textcolor{purple}{CustomerNotFoundException} (errore atteso) viene gestita instradando il messaggio sulla \acrshort{DLQ} e confermando comunque l'\textit{offset}.
Un'eccezione imprevista, invece, lascia l'\textit{offset} non confermato, così da consentire un nuovo tentativo di elaborazione al riavvio del \textit{consumer}.
% Si noti come il blocco \textcolor{purple}{try/catch} traduca direttamente in codice la decisione progettuale illustrata al passo 4-6 dello schema in Y.2.3: la \textcolor{purple}{CustomerNotFoundException} (errore atteso) viene gestita instradando il messaggio sulla DLQ e confermando comunque l'offset (il messaggio è stato "gestito", seppur con esito negativo); un'eccezione imprevista, invece, lascia l'offset non confermato, così da consentire un nuovo tentativo di elaborazione al riavvio del consumer. \\ \\

\subsection{Producer}
La classe \textcolor{purple}{EnrichedProducer} si occupa della pubblicazione, sia sul topic di \textit{output} sia sulla \acrshort{DLQ}:
\begin{codelisting}[H]
\begin{minted}[fontsize=\small,frame=single,framesep=10pt]{java}
@Slf4j
@Component
@RequiredArgsConstructor
public class EnrichedProducer {

    private final KafkaTemplate<String, Object> kafkaTemplate;

    @Value("${app.kafka.topic.output}")
    private String outputTopic;

    @Value("${app.kafka.topic.dlq}")
    private String dlqTopic;

    public void sendEnriched(String key, EnrichedOrder event) {
        kafkaTemplate.send(outputTopic, key, event)
                .whenComplete((result, ex) -> {  });
    }

    public void sendToDlq(String key, Object originalPayload) {
        kafkaTemplate.send(dlqTopic, key, originalPayload)
                .whenComplete((result, ex) -> {  });
    }
}
\end{minted}
\caption{EnrichedProducer}
\end{codelisting}
\noindent
Rispetto alle classi precedenti, qui compare una nuova annotazione:
\begin{itemize}
    \item \textcolor{purple}{@Value("\${app.kafka.topic.output}")}: a differenza di \textcolor{purple}{@KafkaListener}, dove il \textit{placeholder} è risolto internamente all'annotazione stessa, \textcolor{purple}{@Value} è un'annotazione generica che può essere applicata a un campo per iniettarvi direttamente un valore letto dalla configurazione. Il campo \textcolor{purple}{outputTopic} viene così valorizzato automaticamente da \nameref{Spring} all'atto della creazione del \gls{Bean}, senza bisogno di leggerlo esplicitamente da un oggetto \textcolor{purple}{Environment}.
\end{itemize}
Il metodo \textcolor{purple}{sendEnriched} utilizza \textcolor{purple}{KafkaTemplate<String, Object>}, il componente ad alto livello fornito da \nameref{Spring Kafka} per la produzione di messaggi (analogo, sul lato \textit{producer}, a ciò che \textcolor{purple}{@KafkaListener} rappresenta sul lato \textit{consumer}). \\ \\
Il metodo \textcolor{purple}{send(...)} restituisce un \textcolor{purple}{CompletableFuture}, sul quale viene registrata tramite \textcolor{purple}{whenComplete(...)} una \textit{callback} asincrona per il \textit{logging} dell'esito della pubblicazione, \textit{pattern} coerente con la natura non bloccante dell'invio dei messaggi Kafka.
